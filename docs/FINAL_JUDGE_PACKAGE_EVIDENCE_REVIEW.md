# Final Judge Package Evidence Review

Date: 2026-09-10

Purpose: freeze the competition-facing claim boundary against the currently accepted deterministic evidence before public packaging. This document is a review contract, not a marketing page and not execution authority.

## Accepted evidence that may be shown

The final package may demonstrate, when regenerated from the accepted deterministic path:

- incident-scoped causal evidence and blast-radius reconstruction;
- scoped containment evidence;
- recovery execution/result evidence in synthetic or owned state only;
- explicit residual effects, including irreversible or unsuccessfully compensated effects;
- replay evidence and state-based restoration verification;
- Investigator, Recovery Planner and Skeptic/Verifier advisory outputs, clearly separated from authorization;
- deterministic Advisory Gate acceptance/rejection evidence;
- credential-free deterministic incident reproduction;
- canonical JSON packaging and SHA-256 manifest verification;
- B01-B10 deterministic benchmark/advisory coverage only where backed by the generated measured artifacts.

## Claims that remain prohibited

Do not claim any of the following without separate evidence:

- production security effectiveness or a universal recovery-success rate;
- that an irreversible external effect was undone;
- that model output authorized, executed or restored authority;
- that the source agent can declare itself recovered, erase evidence or restore its own authority;
- live Bedrock or AgentCore security effectiveness;
- WORM storage, remote attestation or externally anchored transparency logging;
- generic prompt-injection prevention, SIEM/EDR replacement, broad IAM or compliance-suite coverage;
- arbitrary production transaction reconstruction from Replay Lab evidence.

## Final deterministic reproduction gate

Before a public submission package is considered ready for owner approval, reproduce the accepted judge path from a clean credential-free environment and retain evidence of all of the following:

1. deterministic incident fixture generation succeeds without AWS credentials or paid model calls;
2. the generated incident evidence validates before packaging;
3. canonical JSON round-trip preserves the validated evidence contract;
4. SHA-256 manifest entries match the packaged bytes;
5. judge-console rendering contains only represented evidence and does not invent missing phases;
6. residual irreversible/externalized effects remain visible after recovery;
7. replay can invalidate a false restoration claim;
8. state-based verification, not model text, is the restoration criterion;
9. any malformed, stale, cross-incident or authority-bearing package input fails closed;
10. the final package contains no credentials, private customer data or hidden execution capability.

## Claim-to-evidence review

Every sentence in the final README/demo/submission material that describes product behavior must map to one of:

- deterministic code path plus exact passing test/CI evidence;
- deterministic generated judge artifact/package evidence;
- explicitly labelled product direction or future integration plan.

If a sentence cannot be mapped, weaken or remove it. Do not infer production effectiveness from synthetic benchmark success.

## Demo narrative boundary

The strongest safe demo story is:

**incident -> cross-agent propagation -> causal blast radius -> scoped containment -> evidence-only investigation -> candidate recovery plan -> skeptical challenge -> deterministic recovery gate -> controlled recovery in synthetic/owned state -> residual truth -> adversarial replay -> state-based verified restoration**

The advisory chain never grants execution authority. Recovery and restoration remain deterministic trust boundaries.

## Remaining owner-only gates

The following remain outside autonomous steward authority:

- AWS login/MFA, credentials or model-access changes;
- new AWS spend or persistent paid resources;
- legal/competition-terms acceptance;
- final public video, Builder or Devpost publishing;
- final competition submission.

## Definition of package-ready

Package-ready means the clean deterministic reproduction above passes, the current-state authority matches accepted `main`, CI is green on the exact package head, all public claims map to evidence, and the remaining work is only owner-gated publishing/submission or an explicitly optional live AWS enhancement.
